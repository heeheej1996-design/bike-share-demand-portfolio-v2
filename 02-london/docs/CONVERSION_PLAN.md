# 런던 데이터 시간별 → 일별 변환 계획안

`data/london_merged.csv`(17,414행, 시간 단위)를 일별 데이터로 집계하는 계획입니다.

- **집계 규칙**: 워싱턴 규칙서([`../../01-washington/docs/HOURLY_TO_DAILY_AGGREGATION.md`](../../01-washington/docs/HOURLY_TO_DAILY_AGGREGATION.md))를 그대로 적용
- **원본 유지**: `weather_code`, `season`은 코드 재매핑 없이 원본 값 그대로 사용
- **컬럼 대조 근거**: [`COLUMN_COMPARISON.md`](COLUMN_COMPARISON.md)
- **구현**: [`../scripts/01_hourly_to_daily.py`](../scripts/01_hourly_to_daily.py)

## 0. 요구사항 반영

| 요구사항 | 반영 |
|---|---|
| 하루에 몇 시간이 기록됐는지 컬럼으로 남기기 | `n_hours` (+ `coverage`) → [3절](#3-결측-시간-처리) |
| `timestamp`에서 연·월·요일 추출 | `yr`, `mnth`, `weekday` → [2절](#2-신규-파생-컬럼) |
| 주말도 휴일도 아닌 날을 `workingday=1` | `(1-is_holiday) × (1-is_weekend)` → [2절](#2-신규-파생-컬럼) |
| `weather_code`, `season` 원본 기준 그대로 | 재매핑·재코딩 없음 → [4절](#4-원본-그대로-두는-컬럼) |
| 결과물 저장 위치 | 문서 `02-london/docs/`, 데이터 `02-london/data/london_daily.csv` |

**원본 파일은 수정하지 않습니다.** `london_merged.csv`는 읽기만 하고, 집계 결과를 별도 파일로 새로 씁니다.

## 1. 입력 → 출력

| | 입력 | 출력 |
|---|---|---|
| 파일 | `data/london_merged.csv` | `data/london_daily.csv` |
| 단위 | 1시간 | 1일 |

## 2. 컬럼별 변환 계획

### 원본 컬럼 집계

컬럼 성격에 따라 워싱턴 규칙서의 네 가지 규칙을 배정합니다.

| 런던 컬럼 | 성격 | 규칙 | 판단 근거 |
|---|---|---|---|
| `cnt` | 누적량 | **`sum`** | 그 시간 동안 발생한 대여 건수. 24시간을 더해야 하루치가 됨 |
| `t1` | 상태량 | **`mean`** | 기온(℃). 더하면 의미 없음 |
| `t2` | 상태량 | **`mean`** | 체감온도(℃) |
| `hum` | 상태량 | **`mean`** | 습도(%) |
| `wind_speed` | 상태량 | **`mean`** | 풍속(km/h) |
| `weather_code` | 순서형 | **`mean` → half-up** | 워싱턴 `weathersit`과 동일 규칙. 주의사항은 [4절](#4-원본-그대로-두는-컬럼) |
| `season` | 날짜 속성 | **`first`** | 상수 검사 통과 (하루 2값인 날 0일) |
| `is_holiday` | 날짜 속성 | **`first`** | 상수 검사 통과. 출력명은 `holiday` |
| `is_weekend` | 날짜 속성 | **`first`** | 상수 검사 통과. 원본 보존 |
| `timestamp` | 그룹 키 | `.dt.normalize()` | 날짜+시각 결합 컬럼이라 날짜만 추출 |

**반올림은 half-up(사사오입)** 을 씁니다. `np.round`·`pandas.round`는 half-even이라 결과가 어긋납니다.

```python
def half_up(s):
    return np.floor(s + 0.5).astype(int)
```

**날짜 속성 상수 검사를 먼저 돌립니다.** `season`·`is_holiday`·`is_weekend`가 하루 안에서 변하는 날이 있으면 `first`가 조용히 틀린 값을 만들므로, 검사에서 걸리면 `ValueError`로 중단합니다. 현재 데이터는 세 컬럼 모두 위반 0일입니다.

### 신규 파생 컬럼

런던 원본에 없어 `timestamp`에서 새로 만드는 컬럼입니다.

| 컬럼 | 계산식 | 주의할 점 |
|---|---|---|
| `dteday` | `timestamp.dt.normalize()` | 그룹 키이자 날짜 컬럼 |
| `instant` | `1 ~ N` (날짜순) | 시간별 일련번호와 의미가 다름. 조인 키로 쓰면 안 됨 |
| `yr` | `year - year_base` | 워싱턴과 같은 0-based. 런던은 2015/16/17 **3개 연도**라 0/1 이분값이 아님 |
| `mnth` | `timestamp.dt.month` (1~12) | |
| `weekday` | `(dayofweek + 1) % 7` | **워싱턴은 0=일요일, pandas는 0=월요일.** 보정하지 않으면 하루씩 밀림 |
| `workingday` | `(1-is_holiday) × (1-is_weekend)` | 아래 참고 |
| `n_hours` | `groupby.size()` | 그날 실제 기록된 시간 수 |
| `coverage` | `n_hours / 24` | 하루 24시간 고정 기준 |

#### `workingday` — `is_weekend`를 그대로 쓰면 안 되는 이유

워싱턴 `workingday`는 "주말도 공휴일도 아닌 날"입니다. 런던 `is_weekend`는 순수 요일 정보라 공휴일이 반영되지 않습니다. 런던의 공휴일 16일이 **전부 평일**이므로, `is_weekend`를 그대로 쓰면 이 16일이 근무일로 잘못 분류됩니다.

```
workingday = (1 - is_holiday) × (1 - is_weekend)
```

검증: `workingday=1`인 날 **505일** = 730일 − 주말 209일 − 평일 공휴일 16일 ✓

### 만들지 않는 컬럼

| 워싱턴 컬럼 | 이유 |
|---|---|
| `casual` | 런던 원본에 이용자 구분이 없음. `cnt` 총합만 존재해 **파생 불가** |
| `registered` | 위와 동일 |

회원/비회원 분리 분석은 런던에 이식할 수 없습니다.

### 최종 출력 스키마 (17개 컬럼)

```
instant, dteday,
season, yr, mnth, holiday, weekday, workingday, is_weekend,
weather_code,
t1, t2, hum, wind_speed,
cnt,
n_hours, coverage
```

워싱턴 `day.csv`의 컬럼 순서(식별자 → 날짜 속성 → 순서형 → 평균 → 합계 → 부가정보)를 따릅니다.

**컬럼 이름은 런던 원본 이름을 유지합니다** — `t1`을 `temp`로 바꾸지 않습니다. 워싱턴 `temp`는 0~1 정규화 값이고 런던 `t1`은 섭씨 원값이라, 이름만 같게 만들면 두 도시 파일을 합쳤을 때 서로 다른 단위가 한 컬럼에 섞여도 알아채기 어렵습니다.

## 3. 결측 시간 처리

### 실측 현황

`coverage = n_hours / 24` — **하루를 24시간 고정으로 봅니다.**

| 항목 | 날짜 수 |
|---|---|
| 24시간 온전 | **696일** |
| 시간이 빠진 날 | **34일** (누락 106시간) |
| coverage < 0.90 | 12일 |
| coverage < 0.75 | 3일 |
| coverage < 0.50 | 1일 |

가장 낮은 날: `2016-06-24`(9시간), `2016-09-03`(12시간), `2016-03-27`(14시간). 그리고 `2016-09-02`는 24시간 전부 결측입니다.

### 처리 방침

1. **0으로 채우지 않습니다.** 행이 없는 것은 "수요가 0"이 아니라 "측정하지 못함"입니다. 0으로 채우면 모델에 더 강한 거짓 신호를 줍니다.
2. **있는 시간만으로 계산합니다.** 24로 나누는 게 아니라 실제 행 수로 나눕니다 (`groupby().mean()` 기본 동작).
3. **`n_hours` / `coverage`를 남깁니다.** 나중에 임계값을 바꿔가며 실험할 수 있고, 모델 성능이 이상할 때 결측 때문인지 바로 확인됩니다.
4. **전부 결측인 날짜는 기본적으로 행을 만들지 않습니다.** `--fill-missing-dates`를 주면 행이 추가되되 집계값은 `0`이 아니라 `NaN`입니다.

```python
train = daily[daily["coverage"] >= 0.90]   # 730일 -> 718일
```

### 서머타임(BST) — 24시간 고정 기준에서 어떻게 잡히는지

`timestamp`는 **런던 현지시각**입니다. 근거는 봄 전환일 `2015-03-29`에 1시 다음이 3시로 건너뛰어 2시가 아예 없다는 점입니다 — UTC라면 생기지 않는 구멍입니다.

즉 서머타임 전환일은 **하루가 실제로 23시간 또는 25시간**입니다. 이 계획은 분모를 **24로 고정**하므로, 전환일 4일은 다음과 같이 잡힙니다.

| 날짜 | 실제 하루 길이 | `n_hours` | `coverage` | 해석 |
|---|---|---|---|---|
| 2015-03-29 | 23시간 (봄) | 23 | 0.958 | 다 있는데도 **결측처럼 보임** |
| 2015-10-25 | 25시간 (가을) | 23 | 0.958 | 실제로 2시간 부족 |
| 2016-03-27 | 23시간 (봄) | 14 | 0.583 | 실제 결측 |
| 2016-10-30 | 25시간 (가을) | 23 | 0.958 | 실제로 2시간 부족 |

**알고 넘어갈 점** — `2015-03-29`는 그날 있어야 할 23시간이 전부 있는데도 `coverage=0.958`로 잡힙니다. 분모를 24로 고정한 대가이며, 730일 중 1일에만 해당합니다. `coverage >= 0.90` 기준으로 거르면 이 날은 통과하므로 실무상 영향은 없습니다.

타임존 기준으로 하루 길이를 정확히 계산하면 이 1일을 `coverage=1.0`으로 만들 수 있지만, 계산이 복잡해지고 실습에서 얻는 것이 적어 **24시간 고정으로 단순화**했습니다.

## 4. 원본 그대로 두는 컬럼

### `weather_code` — 재매핑하지 않습니다

워싱턴과 동일한 규칙(평균 → half-up)을 **원본 코드에 그대로** 적용합니다. 심각도 등급으로 바꾸는 매핑 테이블을 두지 않습니다.

**이유** — 매핑 테이블은 새 코드가 등장할 때마다 사람이 손을 대야 합니다. 런던 데이터셋의 코드 체계에는 이 파일에 나타나지 않는 `94`(어는 안개)도 정의되어 있어서, 다른 기간 데이터를 넣으면 매핑에 구멍이 생깁니다. 원본 코드를 그대로 평균 내면 어떤 코드가 들어와도 코드 수정 없이 돌아갑니다.

**알고 쓸 것** — 이 선택에는 대가가 있습니다.

| | 워싱턴 `weathersit` | 런던 `weather_code` |
|---|---|---|
| 값 | 1, 2, 3, 4 | 1, 2, 3, 4, 7, 10, 26 |
| 간격 | 일정 (연속 등급) | **불규칙 (기상청 코드)** |
| 평균의 의미 | 등급의 중간값 | **코드 사이 빈 구간에 떨어짐** |

코드 의미는 1=맑음, 2=구름 조금, 3=구름 많음, 4=흐림, 7=비, 10=뇌우, 26=눈입니다. 간격이 일정하지 않으므로 평균 결과가 **730일 중 56일에서 원본에 없는 값(`5, 6, 8, 9`)** 이 됩니다. 예: 2015-01-15은 맑음·구름·비·눈이 섞여 평균 5.92 → `6`인데, 코드 `6`은 존재하지 않습니다.

`26`(눈)이 유독 큰 숫자라 눈이 몇 시간만 와도 그날 평균을 크게 끌어올립니다. 집계된 `weather_code`는 날씨 등급이라기보다 **"눈·뇌우가 있었는지"를 반영하는 값**에 가깝습니다. 선형회귀에 순서형으로 넣으면 "코드 1 증가"가 일정한 의미를 갖지 않으니, 트리 모델을 쓰거나 범주형 처리를 검토하세요.

변환 스크립트가 실행할 때마다 이 사실을 콘솔에 경고로 출력합니다.

### `season` — 코드를 워싱턴에 맞추지 않습니다

집계 규칙은 `first`로 동일하지만, 두 데이터의 `season`은 **같은 것을 가리키지 않습니다.**

| | 전환일 | 계절 정의 | 코드 의미 (데이터 기준) |
|---|---|---|---|
| 워싱턴 | 3/21, 6/21, 9/23, 12/21 | **천문학적** (춘분·하지·추분·동지) | 1=겨울, 2=봄, 3=여름, 4=가을 |
| 런던 | 3/1, 6/1, 9/1, 12/1 | **기상학적** (월 시작) | 0=봄, 1=여름, 2=가을, 3=겨울 |

`(x+1)%4+1`로 워싱턴 번호에 맞출 수는 있지만, 번호만 같아지고 가리키는 날짜 구간은 최대 3주 어긋난 채 남습니다(3월 10일 = 런던 "봄", 워싱턴 "겨울"). 같은 숫자를 붙이면 이 차이가 보이지 않게 되므로 **런던 원본 코드(0~3)를 그대로 유지**합니다.

## 6. 검증 계획

런던에는 정답지에 해당하는 일별 원본 파일이 **없습니다.** 워싱턴 규칙서 부록 A의 "후보를 전부 계산해 원본과 대조" 방식을 쓸 수 없으므로, 집계 방식을 데이터로 확정할 수 없고 **컬럼 성격 판단에만 의존**합니다. 이 계획의 규칙은 검증된 것이 아니라 이식한 것입니다.

대신 아래 항목을 독립 재계산으로 확인합니다.

| 항목 | 확인 방법 | 결과 |
|---|---|---|
| `cnt` 합계 | 일별 합계 총합 == 시간별 총합 | ✅ |
| `t1`/`t2`/`hum`/`wind_speed` | `groupby.mean()` 재계산과 대조 | ✅ |
| `weather_code` | `floor(mean+0.5)` 재계산과 대조 | ✅ |
| `season`/`holiday`/`is_weekend` | `groupby.first()` 재계산과 대조 | ✅ |
| 날짜 속성 상수성 | `nunique() > 1`인 날 0건 | ✅ |
| `weekday` | 실제 요일명과 대조 (0=Sunday) | ✅ |
| `workingday` | 505 == 730 − 209 − 16 | ✅ |
| `instant` | `1..730` 연속 | ✅ |
| 24시간 온전 696일 / 빠진 날 34일 (106시간) | 개수 확인 | ✅ |
| 연도별 2015 362일 · 2016 365일 · 2017 3일 | 개수 확인 | ✅ |
| `coverage` | `n_hours / 24` | ✅ |
| 결측치 | 출력 파일 `NaN` 0개 (기본 모드) | ✅ |

이 검증은 "코드가 계획대로 동작하는지"를 확인할 뿐, **"집계 규칙 자체가 런던에 맞는지"는 증명하지 못합니다.** 후자는 런던 일별 원본을 구해야 판정할 수 있습니다.
