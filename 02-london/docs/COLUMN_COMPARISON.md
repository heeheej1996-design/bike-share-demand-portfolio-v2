# 워싱턴 ↔ 런던 컬럼 대조 (배경 분석)

워싱턴 규칙서([`../../01-washington/docs/HOURLY_TO_DAILY_AGGREGATION.md`](../../01-washington/docs/HOURLY_TO_DAILY_AGGREGATION.md))를 런던 데이터에 적용하면서, 컬럼을 대조하고 판단한 내용입니다. 구현은 [`../scripts/01_hourly_to_daily.py`](../scripts/01_hourly_to_daily.py)에 있습니다.

**집계 규칙은 워싱턴과 동일하게 적용했습니다.** `weather_code`도 재매핑 없이 원본 코드 그대로 평균 → half-up 반올림을 썼습니다. 그 결과 생기는 문제는 [4절](#4-weather_code-원본-코드를-그대로-쓴-결과)에 정리해 두었습니다.

## 1. 두 데이터 비교

| | 워싱턴 `bike_sharing_hour.csv` | 런던 `london_merged.csv` |
|---|---|---|
| 행 수 | 17,379 | 17,414 |
| 컬럼 수 | 17 | 10 |
| 기간 | 2011-01-01 ~ 2012-12-31 | 2015-01-04 ~ 2017-01-03 |
| 달력상 일수 | 731일 | 731일 |
| **집계 결과 행 수** | **731일** | **730일** |
| 날짜 컬럼 | `dteday` + `hr` (분리) | `timestamp` (결합) |
| 시간대 | 서머타임 없음 | **`Europe/London`, BST 전환 있음** |
| 검증용 일별 원본 | `day.csv` 있음 | **없음** |

런던이 730일인 이유는 `2016-09-02`가 24시간 전부 결측이라 그룹 자체가 만들어지지 않기 때문입니다.

**검증 제약** — 런던에는 정답지에 해당하는 일별 원본 파일이 없습니다. 워싱턴 규칙서 부록 A의 "후보를 전부 계산해 원본과 대조" 방식을 쓸 수 없으므로, 집계 방식을 데이터로 확정할 수 없고 **컬럼 성격 판단에만 의존**합니다. 이 문서의 규칙은 검증된 것이 아니라 이식한 것입니다.

## 2. 컬럼 대응표

| 런던 컬럼 | 워싱턴 대응 | 종류 | 규칙 | 비고 |
|---|---|---|---|---|
| `timestamp` | `dteday`+`hr` | 그룹 키 | `.dt.normalize()` | 결합 컬럼이라 날짜 추출 필요 |
| `cnt` | `cnt` | 누적량 | `sum` | |
| `t1` | `temp` | 상태량 | `mean` | **단위 다름**: ℃ 원값 vs 0~1 정규화 |
| `t2` | `atemp` | 상태량 | `mean` | **단위 다름**: ℃ 원값 vs 0~1 정규화 |
| `hum` | `hum` | 상태량 | `mean` | **단위 다름**: % vs 0~1 |
| `wind_speed` | `windspeed` | 상태량 | `mean` | **단위 다름**: km/h vs 정규화 |
| `weather_code` | `weathersit` | 순서형 | `mean` → half-up | **코드 체계 다름**, [4절](#4-weather_code-원본-코드를-그대로-쓴-결과) |
| `season` | `season` | 날짜 속성 | `first` | **코드·정의 다름**, [3절](#3-season-은-번호도-경계도-다릅니다) |
| `is_holiday` | `holiday` | 날짜 속성 | `first` | 그대로 `holiday`로 출력 |
| `is_weekend` | *(없음)* | 날짜 속성 | `first` | 원본 보존. `workingday`와 **다름** |

컬럼 이름은 **런던 원본 이름을 유지**했습니다(`t1`을 `temp`로 바꾸지 않음). 단위와 코드 체계가 다른데 이름만 같게 만들면, 두 도시 파일을 합쳤을 때 정규화된 값과 섭씨 원값이 한 컬럼에 섞여도 알아채기 어렵습니다.

### 새로 만든 컬럼

런던 원본에 없어서 날짜에서 파생한 것들입니다.

| 컬럼 | 만드는 법 | 주의한 점 |
|---|---|---|
| `dteday` | `timestamp.dt.normalize()` | |
| `instant` | `1 ~ N` 재생성 | 시간별 일련번호와 의미가 다름 |
| `yr` | `year - year_base` | 워싱턴과 같은 0-based. 런던은 **3개 연도**(2015/16/17)에 걸쳐 0/1 이분값이 아님 |
| `mnth` | `timestamp.dt.month` | |
| `weekday` | `(dayofweek + 1) % 7` | **워싱턴은 0=일요일, pandas는 0=월요일.** 보정하지 않으면 하루씩 밀림 |
| `workingday` | `(1-is_holiday) × (1-is_weekend)` | `is_weekend`를 그대로 쓰면 안 되는 이유는 아래 |
| `n_hours` | `g.size()` | |
| `coverage` | `n_hours / 24` | 하루 24시간 고정 기준 |

**`is_weekend` ≠ `workingday`** — 워싱턴 `workingday`는 "주말도 공휴일도 아닌 날"입니다. 런던 `is_weekend`는 순수 요일 정보라 공휴일이 반영되지 않습니다. 런던의 공휴일 16일은 **전부 평일**이므로, `is_weekend`를 `workingday` 대신 쓰면 이 16일이 근무일로 잘못 분류됩니다. 결과: `workingday=1`인 날 505일 = 730일 − 주말 209일 − 평일 공휴일 16일.

### 만들 수 없는 컬럼

| 워싱턴 컬럼 | 상황 |
|---|---|
| `casual` | 런던 원본에 이용자 구분이 없음. `cnt` 총합만 존재 |
| `registered` | 위와 동일 |

회원/비회원 분리 분석은 런던에 이식할 수 없습니다. 두 도시 공통 스키마를 만든다면 이 두 컬럼은 빠져야 합니다.

## 3. `season` 은 번호도 경계도 다릅니다

집계 규칙은 `first`로 동일하지만, 두 데이터의 `season`은 **같은 것을 가리키지 않습니다.**

| | 전환일 | 계절 정의 | 코드 의미 (데이터 기준) |
|---|---|---|---|
| 워싱턴 | 3/21, 6/21, 9/23, 12/21 | **천문학적** (춘분·하지·추분·동지) | 1=겨울, 2=봄, 3=여름, 4=가을 |
| 런던 | 3/1, 6/1, 9/1, 12/1 | **기상학적** (월 시작) | 0=봄, 1=여름, 2=가을, 3=겨울 |

> 워싱턴 `season=1`은 12/21~3/20 구간이므로 겨울입니다. UCI 원본 문서에는 `1:springer`로 적혀 있으나 데이터와 맞지 않습니다.

**런던 원본 코드(0~3)를 그대로 유지했습니다.** `(x+1)%4+1`로 워싱턴 번호에 맞출 수는 있지만, 번호만 같아지고 가리키는 날짜 구간은 최대 3주 어긋난 채로 남습니다(3월 10일 = 런던 "봄", 워싱턴 "겨울"). 같은 숫자를 붙이면 이 차이가 보이지 않게 되므로 매핑하지 않았습니다.

두 도시를 실제로 비교할 때는 원본 컬럼을 맞추지 말고, **날짜에서 하나의 정의로 양쪽 다 새로 계산한 컬럼**을 따로 만드는 편이 안전합니다.

## 4. `weather_code` — 원본 코드를 그대로 쓴 결과

워싱턴과 동일한 규칙(평균 → half-up)을 원본 코드에 적용했습니다. **그 결과 730일 중 56일이 원본 코드 체계에 없는 값이 됩니다.**

원본에 등장하는 코드는 `1, 2, 3, 4, 7, 10, 26` 일곱 개인데, 집계 결과는 `1~10`의 연속값이 나옵니다. `5, 6, 8, 9`가 새로 생긴 값입니다.

| | 워싱턴 `weathersit` | 런던 `weather_code` |
|---|---|---|
| 값 | 1, 2, 3, 4 | 1, 2, 3, 4, 7, 10, 26 |
| 간격 | **일정 (연속 등급)** | **불규칙 (기상청 코드)** |
| 평균의 의미 | 등급의 중간값 | 코드 사이 빈 구간에 떨어짐 |

코드 의미는 1=맑음, 2=구름 조금, 3=구름 많음, 4=흐림, 7=비, 10=뇌우, 26=눈입니다. 예를 들어 2015-01-15은 맑음·구름·비·눈이 섞인 날이라 평균이 5.92 → `6`이 되는데, `6`이라는 코드는 존재하지 않습니다.

`26`(눈)이 다른 코드보다 숫자가 훨씬 커서, 눈이 몇 시간만 와도 그날 평균을 크게 끌어올립니다. 즉 집계된 `weather_code`는 **날씨 등급이라기보다 "눈·뇌우가 있었는지"를 반영하는 값**에 가깝습니다.

### 그래도 이 방식을 쓴 이유

집계 규칙을 워싱턴과 동일하게 가져가기로 했고, 코드 재매핑 테이블을 두면 **새 코드가 등장할 때마다 사람이 손을 대야 하기 때문**입니다. 런던 데이터셋의 코드 체계에는 이 파일에 나타나지 않는 `94`(어는 안개)도 정의되어 있어서, 다른 기간 데이터를 넣으면 매핑 테이블에 구멍이 생깁니다. 원본 코드를 그대로 평균 내면 어떤 코드가 들어와도 코드 수정 없이 돌아갑니다.

### 쓸 때 주의할 것

- **`weather_code`를 순서형 등급으로 모델에 넣으면 간격이 왜곡됩니다.** 트리 모델은 분기 기준만 찾으므로 영향이 작지만, 선형회귀에서는 "코드 1 증가"가 일정한 의미를 갖지 않습니다.
- **범주형으로 원-핫 인코딩할 때는 집계 후 값(1~10)이 원본 코드가 아니라는 점**을 기억해야 합니다.
- 변환 스크립트가 실행할 때마다 이 문제를 콘솔에 경고로 출력합니다.

## 5. 결측 시간

워싱턴과 마찬가지로 결측이 있습니다. `coverage`는 **하루 24시간 고정 기준**(`n_hours / 24`)입니다.

| 항목 | 날짜 수 |
|---|---|
| 24시간 온전 | 696일 |
| 시간이 빠진 날 | 34일 (누락 106시간) |
| coverage < 0.90 | 12일 |
| coverage < 0.75 | 3일 |
| coverage < 0.50 | 1일 |

가장 낮은 날: `2016-06-24` (9/24, 0.375), `2016-09-03` (12/24, 0.500), `2016-03-27` (14/24, 0.583).

### 서머타임(BST)

`timestamp`는 **런던 현지시각**입니다. 근거는 봄 전환일 `2015-03-29`에 1시 다음이 3시로 건너뛰어 2시가 아예 없다는 점입니다 — UTC라면 생기지 않는 구멍입니다.

서머타임 전환일은 하루가 실제로 23시간 또는 25시간이지만, **분모를 24로 고정**했습니다.

| 날짜 | 실제 하루 길이 | `n_hours` | `coverage` |
|---|---|---|---|
| 2015-03-29 | 23시간 (봄) | 23 | 0.958 |
| 2015-10-25 | 25시간 (가을) | 23 | 0.958 |
| 2016-03-27 | 23시간 (봄) | 14 | 0.583 |
| 2016-10-30 | 25시간 (가을) | 23 | 0.958 |

`2015-03-29`는 있어야 할 23시간이 전부 있는데도 결측처럼 잡히지만, 730일 중 1일이고 `coverage >= 0.90` 필터를 통과하므로 실무상 영향이 없습니다.

### 결측을 0으로 채우지 않았습니다

워싱턴 규칙서 4절과 같습니다. 행이 없는 것은 "수요가 0"이 아니라 "측정하지 못함"입니다. `--fill-missing-dates`를 주면 `2016-09-02` 행이 추가되지만, 집계값은 `0`이 아니라 `NaN`으로 남습니다.

학습에 쓸 때는 `coverage`로 거르는 것을 권장합니다.

```python
train = daily[daily["coverage"] >= 0.90]   # 730일 -> 718일
```

## 6. 다른 기간 데이터를 넣을 때

스크립트는 경로와 기준연도를 인자로 받으므로 코드 수정이 필요 없습니다.

```bash
python3 scripts/01_hourly_to_daily.py --input data/london_2018.csv \
                                      --output data/london_2018_daily.csv \
                                      --year-base 2015
```

주의할 점은 두 가지입니다.

1. **`--year-base`를 반드시 지정하세요.** 기본값은 그 파일의 첫 연도라, 지정하지 않으면 2018년 파일에서도 `yr=0`이 나와 2015년 파일과 섞을 수 없습니다.
2. **컬럼 이름이 다르면** 스크립트 상단의 `TS_COL` / `SUM_COLS` / `MEAN_COLS` / `ROUND_COLS` / `CONST_COLS` 상수만 고치면 됩니다.

날짜 속성 상수 검사(`check_constant`)는 매 실행마다 자동으로 돌고, 하루 안에서 `season`·`is_holiday`·`is_weekend`가 변하는 날이 있으면 조용히 넘어가지 않고 `ValueError`로 멈춥니다.
